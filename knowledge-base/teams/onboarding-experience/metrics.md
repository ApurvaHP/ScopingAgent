# Onboarding Experience — Success Metrics Reference

Real metrics this team already tracks, so a new ask can be tied to the metric it should move — instead of inventing a new one each time.

| Metric | Where it's used | Baseline / precedent |
|---|---|---|
| Conversion lift | Foundational launch metrics | Unified Onboarding: 17% conversion lift vs. legacy TRON |
| Net new users | Foundational launch metrics | Unified Onboarding: 42K net new users at launch |
| Annualized revenue | Foundational launch metrics | Unified Onboarding: $29M annualized revenue attributed |
| Net New Actives (NNA) + incremental revenue | Feature-level launches (AI-powered features especially) | GTKM: 4.7K incremental Net New Actives, $1.1M incremental revenue |
| Risk decision latency | Anything touching real-time risk streaming | Cut from ~20s to ~8s via field-level streaming |
| Integration time for a new product team | Anything touching the props-based extensibility contract | Cut from 2 weeks to 3 days |
| Release frequency | Overall team velocity | 2x/week, up from once every 2 weeks |
| Operational time | Process/tooling investments (Definition of Done, AI-assisted release, on-call runbook) | 20% reduction |

## Guidance for new asks

- If an ask doesn't map to any metric on this list, that's a flag, not a blocker — but Product should be asked directly what metric will define success before committing (see `strategicQuestions.forProduct` in the triage output).
- Compliance/legal-driven asks (Amex consent, KYC steps) don't need a growth metric — "delivered on time, zero incidents" is the metric. Don't force a conversion-lift framing onto a compliance requirement.
- Anything claiming a "quick win" should specify which of the above metrics it's a quick win *for* — a quick win with no metric attached is usually a sign the ask isn't scoped yet.
